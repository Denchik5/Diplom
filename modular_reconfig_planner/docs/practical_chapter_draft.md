# Практическая реализация программно-имитационного комплекса планирования реконфигурации модульного робота

## 1. Постановка задачи практической реализации

Практическая часть выпускной квалификационной работы направлена на разработку программно-имитационного комплекса, демонстрирующего алгоритм планирования реконфигурации автономного модульного робота с адаптивной кинематической структурой. В качестве объекта моделирования рассматривается упрощённая SMORES-подобная кинематическая модель модульного робота, состоящая из восьми однотипных модулей. Каждый модуль представлен в виде кубоида с геометрическими размерами 0,22 м по длине, 0,18 м по ширине и 0,10 м по высоте.

Цель практической реализации состоит не в построении физически точной модели реального робота SMORES, а в имитационной проверке алгоритма выбора целевых конфигураций при прохождении участков среды различного типа. Такой подход соответствует задачам бакалаврской работы, поскольку позволяет сосредоточиться на алгоритмической стороне реконфигурации: представлении робота в виде графа, выборе допустимой конфигурации, проверке ограничений, вычислении функции стоимости и формировании последовательности переходов.

Рассматриваются следующие типы среды: ровная поверхность, узкий проход, неровная поверхность, ступенька, зазор и целевая зона. Для каждого типа среды задана базовая целевая конфигурация: `WIDE_STABLE`, `LINE`, `SNAKE`, `CLIMB`, `BRIDGE` и `MANIPULATOR` соответственно. Допускается расширение библиотеки конфигураций, при котором для одного типа среды может существовать несколько допустимых вариантов. В этом случае выбор осуществляется по минимальному значению функции стоимости.

## 2. Архитектура программного комплекса

Программный комплекс построен по модульному принципу. В его состав входят следующие основные подсистемы:

1. модель робота;
2. модель среды;
3. библиотека целевых конфигураций;
4. классификатор среды;
5. модуль проверки ограничений;
6. функция стоимости;
7. планировщик реконфигурации;
8. интерфейс взаимодействия с CoppeliaSim через ZeroMQ Remote API;
9. модуль логирования и сохранения метрик;
10. набор сценариев экспериментов.

Такое разделение позволяет независимо изменять описание конфигураций, правила классификации среды, критерии оптимизации и способ исполнения плана. В offline-режиме комплекс выполняет только расчёт плана и сохранение метрик. В режиме CoppeliaSim выбранные целевые положения модулей передаются в сцену, где движение выполняется кинематически с использованием интерполяции.

Исходные данные задаются в JSON-файлах. Конфигурации робота находятся в каталоге `configurations`, сценарии экспериментов — в каталоге `scenarios`, веса функции стоимости — в файле `weights/default_cost_weights.json`. Результаты моделирования сохраняются в каталог `results` в формате CSV.

## 3. Модель модульного робота

Робот представлен как совокупность восьми модулей `Module_0`, `Module_1`, ..., `Module_7`. Каждый модуль содержит положение в пространстве, ориентацию, набор условных углов суставов и статус. В программной модели используются структуры `ModuleState`, `Module`, `RobotGraph` и `Configuration`.

Топология робота описывается графом `RobotGraph`. Вершинами графа являются модули, а рёбрами — межмодульные соединения. Рёбра содержат номера соединяемых модулей и условные названия соединителей, например `RIGHT`, `LEFT`, `FRONT`, `BACK`. В рамках данной реализации физический механизм стыковки, магнитные защёлки и контактная динамика не моделируются. Ребро графа трактуется как логическое соединение, необходимое для проверки связности и оценки числа изменений соединений при переходе между конфигурациями.

Целевая конфигурация `Configuration` содержит:

- имя конфигурации;
- список целевых положений и ориентаций восьми модулей;
- граф соединений;
- габаритные ограничения;
- оценку устойчивости;
- допустимые типы среды.

Такой способ описания позволяет формировать реконфигурацию как переход от текущего набора положений модулей к целевому набору положений.

## 4. Модель среды

Состояние среды задаётся структурой `EnvironmentState`. Она включает тип среды, список препятствий, параметры целевой зоны и численные параметры, влияющие на выбор конфигурации: ширину коридора, высоту ступеньки, ширину зазора и показатель неровности поверхности.

Препятствия описываются упрощёнными прямоугольными ограничивающими объёмами. Для каждого препятствия задаются идентификатор, тип, положение и размеры. В offline-режиме эти данные используются для оценки минимального зазора до препятствий и риска столкновения. В режиме CoppeliaSim аналогичные объекты создаются в сцене для визуальной проверки работы алгоритма.

Среда не рассматривается как физически точная модель контакта модулей с поверхностью. Она служит источником геометрических ограничений, которые должны быть учтены при выборе целевой формы робота.

## 5. Алгоритм выбора конфигурации

Алгоритм выбора конфигурации выполняется в несколько этапов. Сначала классификатор среды определяет тип текущего участка. Если тип среды явно задан в JSON-сценарии, он используется напрямую. Если тип не задан, классификация выполняется по численным признакам: ширине коридора, высоте ступеньки, ширине зазора, неровности поверхности и признаку достижения целевой зоны.

Далее из библиотеки конфигураций выбираются кандидаты, допустимые для данного типа среды. Для каждого кандидата выполняется проверка ограничений. Недопустимые конфигурации исключаются из рассмотрения. Для оставшихся кандидатов вычисляется значение функции стоимости. Победителем становится конфигурация с минимальным значением стоимости.

Для базового набора сценариев используется следующее соответствие:

```text
FLAT -> WIDE_STABLE
NARROW_PASSAGE -> LINE
ROUGH_SURFACE -> SNAKE
STEP -> CLIMB
GAP -> BRIDGE
TARGET_ZONE -> MANIPULATOR
```

После выбора целевой конфигурации планировщик строит последовательность переходов от текущей конфигурации к целевой. Для демонстрационной реализации используется небольшой граф переходов между известными формами. Это упрощает построение плана и делает работу алгоритма наглядной.

## 6. Проверка ограничений

Модуль проверки ограничений получает текущий граф робота, целевую конфигурацию и состояние среды. В результате возвращается логический признак допустимости, список нарушений и численные значения основных ограничений.

Проверяются следующие условия:

1. связность текущего графа робота;
2. связность целевого графа конфигурации;
3. соблюдение ограничений по углам суставов;
4. геометрическая проходимость для текущего типа среды;
5. соблюдение ограничений по ширине, длине и высоте конфигурации;
6. достаточный запас устойчивости;
7. минимальный зазор до препятствий.

Для оценки устойчивости используется упрощённый геометрический показатель. Он определяется по положению центра масс относительно опорной области, образованной нижними модулями. Данная оценка не заменяет полноценный динамический анализ, но позволяет ввести штраф за потенциально неустойчивые конфигурации.

Минимальный зазор до препятствий вычисляется на основе расстояния между ограничивающими объёмами модулей и препятствий. Неровности поверхности и ступенька могут трактоваться как элементы рельефа, а не как запрещённые объёмы, поэтому они не всегда приводят к отклонению конфигурации по признаку столкновения.

## 7. Функция стоимости

Для выбора оптимального кандидата используется функция стоимости:

```text
J = wT*T + wE*E + wC*C + wR*R + wS*S
```

где `T` — оценка времени реконфигурации, `E` — оценка энергозатрат, `C` — число изменений соединений, `R` — риск столкновений, `S` — штраф за недостаточную устойчивость. Веса `wT`, `wE`, `wC`, `wR`, `wS` задаются в отдельном JSON-файле, что позволяет изменять приоритеты планирования без перекомпиляции программы.

Оценка времени зависит от максимального перемещения модуля, суммарного изменения условных углов суставов и числа изменений соединений. Оценка энергозатрат зависит от суммарного перемещения модулей, изменения углов и топологической перестройки. Риск столкновений определяется по минимальному зазору до препятствий. Штраф устойчивости возрастает, если рассчитанный запас устойчивости меньше требуемого.

## 8. Интеграция с CoppeliaSim

Интеграция с CoppeliaSim реализована через интерфейс `CoppeliaSimZmqInterface`. Он предоставляет методы подключения, отключения, чтения позы модуля, задания позы модуля, интерполяционного перемещения, применения целевой конфигурации, запуска и остановки симуляции.

Сцена CoppeliaSim должна содержать объекты `/Robot/Module_0` ... `/Robot/Module_7`. При выполнении плана программа считывает текущие положения модулей, вычисляет целевые положения для выбранной конфигурации и плавно перемещает модули с фиксированным числом шагов. На каждом шаге вызывается пошаговая симуляция.

Важно отметить, что перемещение модулей является кинематическим. Это соответствует цели работы: продемонстрировать алгоритм планирования реконфигурации, а не моделировать контактную динамику, физическую стыковку и реальные приводы модульного робота.

## 9. Сценарии экспериментов

В проект включены семь сценариев:

- `flat.json` — ровная поверхность;
- `narrow_passage.json` — узкий проход;
- `rough_surface.json` — неровная поверхность;
- `step.json` — ступенька;
- `gap.json` — зазор между платформами;
- `target_zone.json` — целевая зона с переходом в манипуляционную форму;
- `full_mission.json` — полный маршрут.

Сценарий `full_mission.json` включает последовательность:

```text
FLAT -> NARROW_PASSAGE -> ROUGH_SURFACE -> STEP -> GAP -> TARGET_ZONE
```

Для каждого участка программа загружает параметры среды, определяет тип среды, выбирает конфигурацию, проверяет ограничения, вычисляет стоимость, строит переход, выполняет переход и сохраняет метрики.

## 10. Метрики

Для каждого запуска формируется отдельный CSV-файл, а также общий файл `summary.csv`. В таблицу сохраняются следующие поля:

- имя сценария;
- тип среды;
- выбранная конфигурация;
- успешность планирования;
- оценка времени реконфигурации;
- число шагов интерполяции;
- число изменений соединений;
- оценка энергозатрат;
- риск столкновений;
- штраф устойчивости;
- минимальный зазор до препятствий;
- итоговая стоимость.

Эти метрики позволяют сравнивать конфигурации между собой и анализировать влияние параметров среды и весов функции стоимости на результат планирования.

## 11. Анализ ожидаемых результатов

Ожидается, что на ровной поверхности алгоритм сохранит широкую устойчивую транспортную форму `WIDE_STABLE`. В узком проходе должна быть выбрана вытянутая форма `LINE`, поскольку она имеет минимальную ширину. На неровной поверхности выбирается форма `SNAKE`, обеспечивающая большую адаптивность к изменениям рельефа. Для ступеньки используется форма `CLIMB` с поднятыми передними модулями. Для зазора выбирается форма `BRIDGE`, увеличивающая длину конструкции. В целевой зоне робот переходит в форму `MANIPULATOR`, содержащую устойчивое основание и поднятую цепочку модулей.

В полном сценарии ожидается последовательная смена конфигураций в соответствии с изменением среды. Значения функции стоимости должны возрастать при увеличении числа изменений соединений, больших перемещениях модулей или уменьшении минимального зазора до препятствий. При изменении весов функции стоимости возможно изменение предпочтений планировщика, если в библиотеке присутствует несколько допустимых конфигураций для одного типа среды.

## 12. Ограничения реализации

Предложенная реализация имеет демонстрационный характер. Основные ограничения состоят в следующем:

1. не моделируется физически точная динамика реального SMORES;
2. стыковочные механизмы и магнитные соединения представлены логическими рёбрами графа;
3. геометрия модулей упрощена до кубоидов;
4. движение между конфигурациями выполняется интерполяцией;
5. силовые ограничения учитываются оценочно через стоимость, устойчивость и допустимость;
6. столкновения оцениваются приближённо по ограничивающим объёмам;
7. библиотека конфигураций задана вручную и может быть расширена в дальнейшей работе.

Несмотря на эти ограничения, комплекс позволяет воспроизводимо проверять алгоритм реконфигурации на наборе модельных сценариев и получать количественные показатели качества планов.

## 13. Выводы по практической части

В практической части разработан программно-имитационный комплекс для демонстрации планирования реконфигурации модульного робота с адаптивной кинематической структурой. Реализована упрощённая SMORES-подобная кинематическая модель, в которой модули представлены кубоидами, а соединения описываются графом. Создана библиотека целевых конфигураций, соответствующих основным типам среды, реализованы классификация среды, проверка ограничений, функция стоимости и планировщик реконфигурации.

Комплекс поддерживает два режима работы: offline-режим для расчёта плана без CoppeliaSim и режим интеграции с CoppeliaSim через ZeroMQ Remote API. Для проведения экспериментов подготовлен набор JSON-сценариев, включая полный маршрут с последовательным прохождением всех участков среды. Результаты сохраняются в CSV-файлы и могут быть использованы для построения таблиц, графиков и выводов в выпускной квалификационной работе.

## Особенности реализации кинематической модели в CoppeliaSim

Для проведения имитационной проверки алгоритма планирования реконфигурации в среде CoppeliaSim была использована не физически точная модель робота SMORES, а SMORES-подобная кинематическая имитационная модель. Такой подход соответствует цели практической части, поскольку основной задачей является проверка алгоритма выбора целевых конфигураций, оценки ограничений и формирования последовательности реконфигурации, а не моделирование контактной динамики, магнитной стыковки и внутренних механизмов реального модульного робота.

В разработанной модели каждый модуль представлен кубоидом с размерами 0,22 x 0,18 x 0,10 м. Модули размещаются как дочерние объекты корневого dummy-объекта `/Robot`. Это позволяет разделить два вида движения: изменение формы робота внутри локальной системы координат `/Robot` и перемещение всей группы модулей как единого объекта по сцене. При реконфигурации целевые положения модулей задаются относительно `/Robot`, а перемещение между участками среды выполняется за счёт плавного смещения корневого объекта. Такой принцип повышает устойчивость демонстрации и предотвращает разрушение сцены при прохождении нескольких участков среды.

Модули в CoppeliaSim работают в кинематическом демонстрационном режиме. Для них отключаются динамические свойства и физическая ответная реакция на столкновения. Это означает, что модули не управляются силами, моментами или скоростями, а их положение и ориентация задаются программно через интерфейс ZeroMQ Remote API. Данное решение обусловлено тем, что прямое программное задание координат динамическим respondable-объектам может приводить к конфликту с физическим движком CoppeliaSim: модули начинают выталкивать друг друга, прыгать или разрушать сцену. В кинематическом режиме реконфигурация становится воспроизводимой и пригодной для демонстрации работы алгоритма.

Плавность реконфигурации обеспечивается интерполяцией между текущими и целевыми положениями модулей. Вместо линейного изменения параметра интерполяции используется функция сглаживания

```text
smoothStep(alpha) = alpha^2 (3 - 2 alpha), alpha in [0, 1].
```

Она обеспечивает нулевое ускорение в начале и конце перехода по сравнению с резкой линейной сменой положения, что делает визуальное движение более естественным. Все модули обновляются синхронно на каждом шаге: сначала вычисляются промежуточные положения всех модулей, затем эти положения передаются в CoppeliaSim, после чего выполняется один шаг симуляции. Это исключает ситуацию, при которой модули перемещаются по одному и визуально разъезжаются.

Для повышения визуальной связности модулей введены соединительные элементы. Топология робота по-прежнему задаётся графом: вершины соответствуют модулям, а рёбра — соединениям между ними. В CoppeliaSim рёбра графа отображаются визуальными соединителями, расположенными между центрами соседних модулей. Соединители не являются физическими шарнирами и не моделируют защёлку или магнитную стыковку; они выполняют роль визуального отображения текущей кинематической структуры. При каждом шаге реконфигурации положение и ориентация соединителей обновляются вместе с положениями модулей.

В демонстрационном режиме предусмотрена возможность безопасного перехода через промежуточные положения. При необходимости включается режим `use_safe_lift`, в котором движение разбивается на три фазы: небольшой подъём модулей, горизонтальное изменение формы и последующее опускание в целевое положение. По умолчанию этот режим выключен, поскольку для визуально связной демонстрации предпочтительно сохранять модули близко друг к другу. Однако параметр может использоваться при отладке сложных переходов или при визуальном пересечении с препятствиями.

Предложенная кинематическая схема имеет ряд ограничений. Она не позволяет оценивать реальные контактные силы, устойчивость при физическом взаимодействии с поверхностью, работу магнитных соединителей и динамические эффекты при столкновениях. Вместе с тем такая модель достаточна для проверки алгоритмической части работы: выбора конфигураций для разных типов среды, проверки геометрических ограничений, расчёта функции стоимости и формирования последовательности реконфигураций. Поэтому в рамках бакалаврской ВКР данная реализация рассматривается как программно-имитационный комплекс для демонстрации принципа планирования реконфигурации, а не как физически точный цифровой двойник реального робота SMORES.
